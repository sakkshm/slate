## 2. Definitive Architecture Roadmap

Here is the step-by-step roadmap to move from a blank directory to a fully functional Vercel-like platform.

### Phase 1: The Isolation & Execution Engine

Focus exclusively on the low-level engine that interfaces with the container runtime. No APIs or queues yet.

* **Step 1.1:** Write the runner module using the official Docker SDK. Initialize a client that talks directly to the local Unix socket (`/var/run/docker.sock`).
* **Step 1.2:** Implement programmatic container creation. Hardcode a Git repository URL, pass it into the container as an environment variable, and run an isolated bash script that performs a shallow clone and runs a build script.
* **Step 1.3:** Build the security profile. Configure the `HostConfig` struct to drop all Linux capabilities (`CapDrop: []string{"ALL"}`), set a non-root execution user, and apply hard cgroup boundaries:
* `Memory`: `512 * 1024 * 1024` (512 MB hard cap)
* `NanoCPUs`: `1000000000` (1.0 CPU Core limit)


* **Step 1.4:** Create the asset extractor. Use Docker's `CopyFromContainer` API endpoint to read the compiled files out of the container as a raw tar-stream after the build finishes successfully. Untar and dump them to a temporary local storage bucket.

### Phase 2: The Event-Driven Pipeline

Introduce asynchronous scaling by decoupling ingestion from compilation.

* **Step 2.1:** Stand up a local Redis instance. Implement a publisher that pushes a structured payload (`Project ID`, `Deployment ID`, `Git Commit Hash`) into a Redis Stream.
* **Step 2.2:** Build the worker thread loop. Implement a consumer group pattern where the worker reads from the stream, explicitly claims a job, and passes the payload directly to the engine written in Phase 1.
* **Step 2.3:** Implement a state tracking framework. When a job is picked up, update the deployment state in Redis to `BUILDING`. If the engine returns an error or a timeout occurs, change the state to `FAILED`. If successful, mark it as `READY`.
* **Step 2.4:** Build log streaming. Capture the live stream output (`stdout`/`stderr`) from the container runtime and continuously pipe it to a Redis key or channel labeled by the deployment ID, utilizing proper buffers to manage high log volume.

### Phase 3: Storage Provider Integration & Distribution

Exfiltrate files from the worker environment to the permanent distribution tier.

* **Step 3.1:** Stand up an instance of MinIO via Docker Compose to serve as your cloud-agnostic S3 object store layer.
* **Step 3.2:** Implement the Storage Interface layer. Take the raw tar stream extracted from the execution engine, calculate a content-addressable hash for the assets, and push them to the object store partitioned by `deployment_id/`.
* **Step 3.3:** Generate a static distribution manifest—a lightweight file catalog detailing the content type, path, and hash mapping for every static file generated by that specific build run.

### Phase 4: Dynamic Edge Routing (The Data Plane)

Serve incoming requests for static sites instantly without complex configuration reloads.

* **Step 4.1:** Build the reverse proxy application layer. It must listen on incoming HTTP traffic and look up the incoming `Host` header (e.g., `app-123.slate.dev`) against the Redis database mappings.
* **Step 4.2:** Resolve the exact routing path to the storage tier. If a request hits `app-123.slate.dev/assets/index.js`, the proxy fetches that exact object directly from the storage layer or an internal memory cache and streams it straight to the client with the proper content headers.

## 3. Virtual Documentation (Architectural Decision)

To maintain our repository state and track the choices made for **Slate**, copy and paste the markdown block below into your root directory files to initialize our architectural baseline.

```markdown
# Slate Virtual Documentation: Architectural Baseline

## Core Systems Architecture
* **Orchestration Model:** Programmatic micro-orchestration using the Docker Engine API over Unix sockets (`/var/run/docker.sock`).
* **Concurrency & Scheduling:** Event-driven worker pool scaled via Redis Streams Consumer Groups ensuring at-least-once delivery guarantees.
* **Runtime Sandbox Boundaries:** Strict single-tenant container isolation using Linux kernel namespaces, dropping all default root capabilities (`CapDrop: ["ALL"]`), and running with zero host filesystem mounts. 
* **Resource Constraints:** Hard limits implemented via cgroups: 512MB RAM maximum ceiling and a 1.0 NanoCPU throttle configuration.
* **Storage & Distribution Tier:** Decoupled object storage layout utilizing S3-compatible APIs (MinIO) with static artifact mapping manifests stored in an active Redis cache.

## Network Data Plane
* **Dynamic Routing Routing:** Domain-to-asset mapping resolved via an active Redis lookup table on the request path, preventing web server reboots or configuration reloads during application lifecycle updates.

```
